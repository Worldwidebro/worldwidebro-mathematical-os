### Newly Discovered — NOT Auto-fixed (Rule 4, requires human decision)

**2. [Rule 4 - Architectural/Infra] Native Homebrew Prometheus process shadows the Docker container's published host port 9090**
- **Found during:** Task 2 verification (the plan's exact `curl http://localhost:9090/api/v1/targets` command kept returning only 1 active target — `prometheus` — even after the container-side reload succeeded)
- **Root cause identified:**
  - `ps aux | grep prometheus` shows a native Homebrew-installed binary running directly on the host: `/opt/homebrew/Cellar/prometheus/3.11.2/bin/prometheus --config.file /opt/homebrew/etc/prometheus.yml --web.listen-address=127.0.0.1:9090 --storage.tsdb.path /opt/homebrew/var/prometheus`, PID 1042, running continuously since **2026-06-25** (well before this task, and before the Docker Compose stack's prometheus service existed in its current form).
  - `lsof -nP -iTCP:9090 -sTCP:LISTEN` confirms this native process is bound to `127.0.0.1:9090` (plus an unrelated `ssh` listener on `*:9090`).
  - `/opt/homebrew/etc/prometheus.yml` contains only a trivial self-scrape job (`job_name: prometheus`, target `localhost:9090`) — this exactly matches the "1 active target: itself" symptom the plan's original problem statement described, and explains why planning's earlier probes of `localhost:9090` also only ever saw 1 target.
  - The Docker container `prometheus` (from `docker-compose.yml`, publishing `9090:9090`) is running correctly and healthy (`docker ps` shows `Up ... (healthy)`), and `docker exec prometheus wget -qO- http://localhost:9090/api/v1/targets` (i.e., querying from *inside* the container's own network namespace, bypassing the host) confirms **4 active targets**: `prometheus`, `otel-collector`, `grafana`, `qdrant`. The Prometheus API's own `/api/v1/status/config` and `/api/v1/status/runtimeinfo` (queried from the host) further corroborate the mismatch: the host-visible instance reports `startTime: "2026-06-25T16:21:58Z"` and a config containing only the single `prometheus` job — this is the native process's own uptime and config, not the container's.
  - Net effect: **the Docker container's work for this task is fully correct and complete**, but it is unreachable via `http://localhost:9090` on the host because an unrelated, pre-existing native process has permanently claimed that port on the loopback interface.
- **Why not auto-fixed:** Killing PID 1042 (`kill 1042` or `brew services stop prometheus`) or changing the Docker Compose port mapping (e.g. `9090:9090` → `9091:9090`) are both infrastructure changes with unknown blast radius — the native process may be relied on by something else on this machine (another dashboard, a personal monitoring habit, a script), and remapping the container's port would require updating anything currently pointing at `http://localhost:9090` for the Docker stack. This is a Rule 4 architectural decision requiring explicit user authorization, not a same-task auto-fix.
- **Recommended next step (for user):** Confirm whether the native Homebrew Prometheus (`brew services list | grep prometheus`, PID 1042) is still needed. If not: `brew services stop prometheus` (or `kill 1042`) frees `127.0.0.1:9090` for the Docker container's already-correct config to become visible at `http://localhost:9090`. If it IS needed for something else, the Docker Compose `prometheus` service's host port should instead be remapped (e.g., `9091:9090` in `docker-compose.yml`), and this quick task's Task 2 verify command re-run against the new port.
- **Files modified:** None — investigation only, no destructive action taken.
- **Verification:** See root-cause evidence above; no fix applied pending user decision.
